Compatibility

Support browsers deliberately and migrate predictably

Nexaline publishes an explicit browser floor, tests current engines as regression evidence, and records breaking beta changes with direct replacements.

Supported browser floor

BrowserMinimum version
Chrome111+
Edge111+
Firefox114+
Safari on macOS16.4+
Safari on iOS16.4+

The canonical values live in config/browser-support.mjs. Package builds and the documentation build consume those targets directly, so compatibility is not inherited accidentally from a bundler default.

What the support floor means

  • Compiled JavaScript syntax targets every declared engine.
  • CSS, keyboard behavior, themes, RTL, and responsive layouts are designed for the declared range.
  • A release candidate must pass Chromium, Firefox, and WebKit automation.
  • A changed floor requires a policy update, rebuilt assets, the full release gate, and a changelog entry.

Automation and manual evidence are different

EvidenceWhat it establishesBoundary
Current Chromium, Firefox, and WebKitRegression coverage for documentation, components, integrations, and accessibility checksDoes not prove the oldest supported versions
WebKit automationCross-engine behavior in the automated suiteDoes not replace native Safari on macOS or iOS
Emulated preferences and touchRepeatable checks for forced colors, reduced motion, viewports, and targetsDoes not replace physical devices or native assistive technology
Recorded manual reviewEnvironment-specific keyboard, screen-reader, zoom, contrast, motion, RTL, and touch observationsApplies only to the recorded versions and hardware
Stable-release requirement: manually smoke-test the oldest supported versions before 1.0, or raise the floor transparently.

Progressive enhancement without JavaScript

Core content, links, native controls, forms, and layout remain useful when JavaScript is unavailable. JavaScript enhances dialogs, drawers, tabs, accordions, dropdowns, toasts, and other stateful behavior.

<button type="submit" class="nx-btn nx-btn--primary">Save</button>

<!-- Add data-nx-* hooks only when enhanced behavior is needed. -->

Do not make essential information available only through an enhanced component. Server validation, normal navigation, and semantic document order remain application responsibilities.

Browsers below the floor

Browsers below the published floor are not tested or supported. Nexaline does not ship a legacy JavaScript bundle or application polyfills.

If an application must support an older engine, test its exact requirements, own any necessary transpilation or polyfills, and avoid claiming that configuration as official Nexaline support.

Pre-1.0 migration policy

Public APIs remain experimental before 1.0. A breaking beta release must list the affected classes, attributes, events, tokens, exports, or methods in CHANGELOG.md and provide the direct replacement.

When practical, a deprecated contract remains available for at least one beta. Security, accessibility, or correctness fixes may require faster removal, which must still be documented.

Pin production betas: use an exact version rather than @beta in deployed applications, then upgrade intentionally after reviewing the changelog.

Migrate from beta.0 to beta.1

No code migration is required. Version 0.1.0-beta.1 preserves the beta.0 API surface. It adds verified npm installation guidance, package metadata, GitHub Pages deployment, and CI resilience.

npm install nexaline-ui@0.1.0-beta.1
# or update each selected @nexaline-ui/* package to 0.1.0-beta.1

Do not mix beta.0 and beta.1 modular packages. Keep @nexaline-ui/core, @nexaline-ui/components, @nexaline-ui/js, and optional adapters on the same release when used together.

Upgrade checklist

  1. Read the target version entry in CHANGELOG.md.
  2. Pin one exact version across all Nexaline packages.
  3. Rebuild committed or deployed CSS and JavaScript assets.
  4. Run application tests for keyboard behavior, focus, forms, themes, RTL, and responsive layouts.
  5. Repeat the native browser and assistive-technology checks required by the application.
  6. Deploy through a reversible release and verify the served asset versions.
